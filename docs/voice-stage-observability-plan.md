# 逐句 TTS 与 ASR → Memory 诊断方案

2026-09-16 的历史设计记录。本文件保留当时的取证与方案，不作为当前待办清单；后续 VAS 埋点已独立开发，实施状态以 VAS dev 代码为准。本文所述 Testing 改动不修改 VAS。

## 本次 Testing 实现

- 用户一次 PTT 录音显示为一条，使用实际开始/停止标志；缺少停止标志时使用最后采集时间并提示。VAD 输入合并句内停顿，保留句前、句后的底噪。不改原始帧、发包时间、音频或播放时钟。
- 每段 TTS 的色块及下方文字入口显示播报文字，悬停或点击看全文。保留分组、颜色、真实起止和独立事件展开。
- 文本按同一服务端会话、明确轮次、完整句消息顺序及逐句字符数核对；音频包归属也一致时标记“按音频包关联”。旧客户端包序号漂移时标记“按句消息顺序关联”。缺失、冲突或未下发句消息的打断片段不猜文本。
- 这些是 WebSocket 播报文本，不能代替精确的 TTS provider 入参。
- 现有 `tts_segment_ready` 显示为“**TTS 分段就绪（消费侧）**”，关联到具体段号与颜色。它不是 LLM 每句文本完整可用的时刻。

## 已有记录告诉了我们什么

### ASR → Memory

`pinned-timeline-20260915` 第一轮，全部为 VAS 同一时钟：

| 事件 | 北京时间 | 距 ASR 最终结果 / s |
|---|---|---:|
| ASR 最终结果 | 17:27:11.882838 | 0 |
| ASR 连接关闭 | 17:27:11.922414 | 0.039576 |
| 护栏 Embedding 开始 | 17:27:11.926578 | 0.043741 |
| Memory 开始 | 17:27:11.931926 | 0.049088 |
| Memory 结束（HTTPError，降级） | 17:27:12.012537 | 0.129699 |
| LLM 开始 | 17:27:12.014393 | 0.131555 |

截图约 0.13 秒包括 Memory 本身的 **0.080611 秒**；ASR 最终结果 → Memory 开始为 **0.049088 秒**。

公共 ASR 收尾依次包含解码/合并音频、缓存转写与可选声纹任务的结果等待、语言/说话人处理、连接清理，再进入聊天。当前检查到的 DashScope 实现同步调用连接 close，位于关键路径，但缺少 close 调用前后的独立测量，不能将全部 0.039576 秒归因于 close。

聊天入口之后还可能执行 Vision 输入构造、后续轮次配置就绪等待、Intent、安全检查、STT 发送、线程池排队、工具列表及提示准备。必须记录实际执行的分支，不能用相邻事件差代替某个函数耗时。

### TTS 请求 → 首个 PCM

`81cdd36806fd4a9c80e32b4341ed3b01` 第一轮第一段总计 **0.289274 秒**：

| 阶段 | 耗时 / s |
|---|---:|
| TTS 请求开始 → 请求 body 发出 | 0.051503 |
| body 发出 → 响应 headers | 0.224245 |
| headers → 首个有效 PCM | 0.013527 |

首阶段包含新建连接 **0.051015 秒**，DNS 为 **0.000730 秒**。后续三段复用连接，首 PCM 分别为 **0.173189 / 0.157104 / 0.154866 秒**。这能说明连接建立的成本，不能证明 MiniMax 模型冷启动。

现有公共 HTTP 埋点已覆盖连接池、DNS、连接复用、body 发出及 headers 返回；现有首 PCM 在解析出有效音频后记录。请求发出到 headers 返回混合了网络、供应商排队及计算，单靠 VAS 本地时间无法进一步准确拆分。先使用已有点；只有 headers → PCM 持续很大，再考虑首 body 字节、首完整 SSE 事件。供应商内部耗时需其 trace 或服务端计时支持。

## VAS 最小公共埋点方案（本次不实施）

### A. 每句可合成文本何时完整到达

当前 `tts_segment_ready` 在 TTS 消费线程实际分句时产生。消费线程可能等待上一段合成，记录会晚于入队；上述真实报告第 2–5 段分别晚 **0.389512 / 0.469868 / 0.623878 / 0.621556 秒**。现有 `text_received_ns` 仅为当前队列项的入队时刻，缺少整句来源，不能直接改名。

建议复用实际分句流程：

1. 公共诊断队列为可播文本块保留输出内字符区间 `[start,end)` 和入队时间。
2. 实际公共分句器为每个片段保留它消费的原文范围，以及标点、flush、流结束等分段原因。若有清洗或结构化输出转换，保留源范围映射，不能按清洗后长度倒推。
3. 将片段与构成它的源文本块及结束信号关联，记录“文本完整可用”和“分段条件满足”的时间。正常标点句取最后所需文本块的到达时间；无标点尾句还必须等 flush/流结束；长度阈值或显式提交遵循真实策略。
4. 保留消费侧 ready、TTS 排队/开始、首 PCM 的独立时间，从而区分 LLM 等待、TTS 排队与合成耗时。
5. 每点带 `clock_id / listen_turn_id / output_id / segment_id / parent LLM span / output_kind / segment_seq`。过渡语、临时回复和工具后正式回答分别归属，打断后的旧输出不串到新轮。

这里测的是 **VAS 收到并解析出足够文本的时刻**，不是云端模型内部生成时刻。不另写预测分句器，不遍历修改 LLM providers。

可保留原有 ready 事件并加 `text_available_ns`、`boundary_ready_ns`、源区间等字段；报告据此创建独立标记。字段晚随消费侧事件回传不影响其原始时间。未具备来源映射的路径明确标记未知。

### B. ASR 最终结果 → Memory

使用统一阶段助手记录公共编排边界：

| 公共阶段 | 用途 |
|---|---|
| ASR 收尾总段 | 承载后续子阶段，不能与子阶段重复求和 |
| 音频解码/合并 | 识别 CPU 与数据整理开销 |
| 转写/声纹结果等待 | 区分可选任务等待和结果读取 |
| ASR 连接清理开始/返回 | 判断 close 是否阻塞关键路径 |
| 聊天接纳 | 记录实际执行的 Vision、配置就绪、Intent、安全检查及 STT 发送子段 |
| 聊天任务入队/开始 | 记录线程池真实排队时间，显式传递轮次上下文 |
| 聊天准备 → Memory | 工具/路由/提示准备等边界；保留现有 Memory 请求 span |

先测量再决定是否异步清理 ASR。直接把 close 放到后台会影响回调、缓冲区和新旧轮次归属，需要另外证明隔离安全。

第一阶段复用 `core/diagnostic_http.py`，无需新增 MiniMax、DashScope、OpenAI 等具体 provider 改动。

### 验收

- 确定性假流：逐块标点、跨块句子、一个块多句、无标点尾句、长度切分、显式 flush、结构化字段与清洗文本。
- 慢 TTS 消费：第 2 句已经可用但排队，完整可用时间不得跟随消费时间后移。
- 工具多轮、过渡语、欢迎语、打断取消、晚到回调、并发会话，关联不串。
- 注入解码、声纹等待、cleanup、线程池排队延迟，记录准确归入对应阶段；Memory 异常保持原有降级。
- 关闭诊断保持原有业务行为；开启、关闭均无新增业务等待；诊断异常不得中止回复。
- 基于部署版本复核：本次代码只读核对了本地 VAS `2ea7d741` 和 `75380cd4`，不能据此断言远端部署 revision。时间结论独立来自上述原始日志。
